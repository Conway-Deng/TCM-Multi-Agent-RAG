## Research questions

- **W-RQ1:** How do retrieval strategies affect gold-evidence retrieval within the frozen MediRAG-West pilot corpus?
- **W-RQ2:** With the generator held fixed, how do retrieval strategies affect evidence coverage and unsupported-claim behavior in generated Western pilot answers?
- **W-RQ3:** How does the system behave when the frozen pilot corpus provides incomplete or insufficient evidence?

## Retrieval conditions

The existing `RetrievalEngine` is used without algorithm changes. Final `top_k=4` for every condition.

| Condition | Existing implementation | Provider/model | Candidate and fusion policy | Rerank |
|---|---|---|---|---|
| R0 | BM25-like lexical scoring | Local deterministic | All topic-filtered chunks ranked lexically | None |
| R1 | Dense cosine similarity | SiliconFlow `BAAI/bge-m3` | All topic-filtered chunks ranked by dense similarity | None |
| R2 | Lexical+dense reciprocal-rank fusion | Local lexical + SiliconFlow `BAAI/bge-m3` | `1/(60+lexical_rank) + 1/(60+dense_rank)` | None |
| R3 | R2 candidates followed by the existing reranker pathway | SiliconFlow `BAAI/bge-m3` and `BAAI/bge-reranker-v2-m3` | Fixed hybrid candidate depth 12 | Rerank 12, return 4 |

Formal-strict mode forbids local fallback and requires the stated provider/model identities. Embeddings use `chunk-text-v1`, embedding configuration `retrieval-ablation-v1`, batch size 64, and a corpus/model-bound persistent cache.

## Denominators and retrieval metrics

Headline retrieval metrics use the 42 supported or partially-supported cases that have non-empty primary gold. The six insufficient cases are reported separately and are not forced into headline gold-recall denominators, even when a boundary/limitation chunk is annotated.

Primary metrics are macro and aggregate Primary-Gold Chunk Recall@4, macro and aggregate Primary-Source Recall@4, MRR of the first primary gold chunk, and Hit@4. Cases with no primary gold are excluded from MRR. Primary-or-secondary Hit@4 and Recall@4 are secondary diagnostics only.

## Fixed generation configuration

- Provider: SiliconFlow
- Model: `Qwen/Qwen3-8B`
- Temperature: 0
- Maximum tokens: 256
- Retrieval top_k: 4
- Evidence excerpt maximum: 1000 characters per retrieved item
- Timeout: 120 seconds
- Prompt: current frozen `WesternEvidenceAgent` prompt and generation contract, unchanged
- Repetitions: one generation per cell

The generator receives labels, titles, sections, and bounded excerpts but no internal provenance identifiers. Application-generated provenance is authoritative.

## Matrix and balanced order

The matrix is 48 cases × 4 retrieval conditions = 192 cells. Case 1 uses R0,R1,R2,R3; case 2 uses R1,R2,R3,R0; case 3 uses R2,R3,R0,R1; case 4 uses R3,R0,R1,R2; the rotation repeats. The committed `execution_order.json` is authoritative. Valid completed cells are never silently rerun.

## Stage separation and immutability

- **Stage A:** retrieval only. Its sealed JSONL and SHA256 manifest become immutable Stage B input.
- **Stage B:** generation only from sealed Stage A. Its sealed JSONL and SHA256 manifest become immutable Stage C input.
- **Stage C:** judging only from sealed Stage A evidence and Stage B answers.

Each cell is uniquely keyed by `(case_id, retrieval_condition)`. Appends are flushed and fsynced; duplicates are rejected. Stage A seals after exactly 192 unique terminal records (`success` plus `technical_failure`), never merely 192 successes. Missing, duplicate, in-progress, corrupt, or fatal-defect states prevent sealing. Technical missingness alone permits sealing after all cells are terminal. A sealed stage cannot be appended to or resumed. A repeated formal run requires a new `run_id`; no run output may be overwritten.

Stage A has an independent finalizer that emits only Stage-A raw results, retrieval metrics, provider metrics, pairwise statistics, its run manifest, and `STAGE_A_FROZEN.md`. It does not require or fabricate Stage B/C artifacts. Excerpt-bearing raw results remain local, immutable, hash-referenced input for Stage B.

## Automated judge

The judge is a distinct SiliconFlow model, `THUDM/GLM-Z1-9B-0414`, with temperature 0, maximum 1200 tokens, and 120-second timeout. It is an `automated_secondary_model`; `human_verified=false` and `domain_expert_verified=false`.

The judge receives the question, generated answer, actual retrieved evidence excerpts, frozen expected evidence points, and answerability label. Retrieval scores are excluded. It returns raw structured JSON with short justifications and no hidden chain-of-thought.

## Insufficient and partial evidence

For the six insufficient cases, appropriate handling means either abstention or a clearly bounded statement that the current pilot evidence cannot answer the requested information need. A topical answer that fails to acknowledge missing evidence is inappropriate. Report abstention, explicit insufficiency, substantive answering despite insufficiency, and overclaiming separately.

For the four partially-supported cases, assess whether the answer stays inside supported evidence, preserves material uncertainty, or invents the unsupported portion. Total abstention is not required.

## Provenance and observable scope behavior

Provenance Integrity Rate is deterministic and application-level: provenance count, top_k membership, source resolution, URL presence, Western-only evidence, and equality with application-generated retrieval metadata. It is not sentence-level citation correctness.

Do not create a clinical safety score. Record only observable diagnosis-like personalization, individualized dosing, prescription-like recommendations, and preservation of research/educational limitation language, using deterministic checks and judge flags where applicable.

## Reliability, latency, and comparisons

Record retrieval, generation, and judge latency separately. Report first-attempt provider success, final completion after the permitted retry, technical failures, retries, and total elapsed time. Technical generation failures retain Stage A retrieval and are excluded from semantic answer-quality denominators with missingness reported.

Primary comparisons are R0–R1, R0–R2, and R0–R3. Their denominator is the successful-pair intersection of frozen gold-eligible cases. Use McNemar for applicable paired binary outcomes. For bounded per-case metrics, report paired differences and 95% paired bootstrap confidence intervals where implemented, with exact sample sizes. Provider failures are excluded without zero imputation and reported separately. Do not overemphasize p-values and do not encode winner/superiority language.

No formal benchmark case was executed while creating or freezing this protocol.

## Upstream technical missingness

A Stage A `technical_failure` cell remains in Stages B and C without a Qwen or GLM call. Stage B records `generation_outcome=upstream_retrieval_technical_failure`, an empty answer/provenance, zero attempts, and zero latency. Stage C records the matching upstream-missing outcome, no semantic labels, zero attempts, and zero latency. This is technical missingness—not abstention, insufficiency handling, content failure, or model failure—and semantic generation/judge denominators exclude it.
